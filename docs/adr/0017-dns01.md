# ADR-0017: DNS-01 challenges and wildcard certificates

**Status:** Accepted (2026-11-21)

## Context
M2 proves domain control only through HTTP-01, which needs a web server reachable from the
CA on port 80. That rules out internal hosts, hosts behind load balancers, and wildcard
certificates (RFC 8555 section 7.1.3 allows wildcards only with DNS-01).

DNS-01 needs write access to DNS, and a credential with that access can obtain a
certificate for any name in the zone. That makes the place where it is stored the main
decision. ADR-0006 already rejected moving the ACME client and DNS credentials into the
control plane.

## Options considered
| Option | For | Against |
|---|---|---|
| **A. Solvers and credentials in the agent's local config** | The control plane never holds DNS write access; same trust model as targets (the control plane names a target, the host decides paths and allowed names) | Credentials are managed per host; rotating one token means touching every host that uses it |
| B. Credentials stored in the control plane (ADR-0009), sent encrypted to one agent per task | Central management and rotation | A control-plane compromise gains DNS write access for every zone; secrets travel and end up on every agent that ever renewed |
| C. Control plane writes the TXT record, agent runs the ACME order | Agents need no DNS credentials | Splits one ACME order across two processes; credentials are concentrated as in B |

## Decision
Option A.

**Agent config**
```yaml
dns_solvers:
  - name: internal
    provider: rfc2136          # lego dnsupdate
    nameserver: 10.0.0.53:53
    tsig_file: /etc/certloom-agent/dns/internal.key   # BIND key file
    zones: [corp.example.com]
  - name: public
    provider: cloudflare
    token_file: /etc/certloom-agent/dns/cloudflare.token
    zones: [example.com]
  - name: corp
    plugin: /usr/libexec/certloom/dns/certloom-dns-corp
    sha256: 3f1c...
    zones: [corp.example.net]
    config: {endpoint: "https://dns.corp.internal"}
resolvers: [10.0.0.53:53]        # optional, for split-horizon DNS
```
- Built-in providers read credentials from files (systemd credentials work), never from
  the config file itself, and pass them to lego through its typed config, not process
  environment variables.
- The agent follows the `_acme-challenge` CNAME first (delegation to a dedicated
  validation zone), then picks the solver whose zone is the longest suffix of the
  resulting name. No match fails the challenge with a permanent error naming the record.
  At config load, every solver zone must be distinct.
- The heartbeat reports solver names, providers and zones, never credentials.

**Providers and plugins**

DNS providers are configurable and open to third parties. There are three tiers, all
selected the same way in `dns_solvers`:

1. **Built-in:** `rfc2136` and `cloudflare`, compiled into the agent and tested by this
   project.
2. **Plugins:** any executable on the agent host that speaks the Certloom DNS plugin
   protocol, in any language. This is the extension point.
3. **`certloom-dns-lego`:** a plugin shipped as a separate binary that exposes every lego
   DNS provider through the same protocol. It keeps those providers (and their
   environment-variable configuration) out of the agent process. These providers are listed
   as "via lego, untested here" until a conformance run or a live test backs one.
   *Not built yet:* many lego providers keep the record id in memory between Present and
   CleanUp, so both calls must run in one process. This waits for the HTTP transport (a
   long-running plugin) or a per-provider answer.

New providers are not added to the agent; they are written as plugins. cert-manager and
ExternalDNS made the same choice (external webhooks) because a core team cannot maintain
every DNS API.

Plugin protocol, version 1:
- The agent runs `<plugin> describe|present|cleanup` directly (no shell) and writes one
  JSON object to stdin:
  `{"protocol":1,"fqdn":"_acme-challenge.example.com.","value":"...","zone":"example.com.","config":{...},"domain":"example.com","token":"...","key_auth":"..."}`.
  `domain`, `token` and `key_auth` let a plugin wrap a client that derives the record
  itself (lego, acme.sh); none of them is secret.
  `describe` returns `{"protocol":1,"name":"...","version":"..."}`.
- The plugin answers with one JSON object on stdout: `{"ok":true}`, or
  `{"error":"...","class":"auth|rate_limited|transient|permanent","retry_after":30}`.
  A non-zero exit without valid JSON is a transient error. Stdout is capped at 64 KiB;
  stderr goes to the agent log.
- `present` and `cleanup` must be idempotent. `fqdn` is the name after CNAME resolution;
  the agent follows CNAMEs, checks propagation and talks to the CA, so a plugin only
  writes and removes TXT records and cannot weaken validation.
- Plugins read their own credentials (files, environment, instance identity). The agent
  passes only the non-secret `config` map from its config file, and an environment holding
  `PATH` plus the variables listed in the solver's `env`.
- The executable must be an absolute path, not writable by group or others, and match the
  `sha256` pinned in the config. Each call has a timeout (default 60s). Plugins run with
  the agent's privileges: installing one is a host-administrator decision, like
  `test_command` and `reload_command`.
- `certloom-agent dns-test --solver NAME --name DOMAIN` is the conformance test for plugin
  authors and the connection check for operators, for any solver: describe (plugins),
  present twice, wait until the record resolves, clean up twice, wait until it is gone.
- The Go SDK is the public package `github.com/alexandrosnt/certloom/dnsplugin` (`Handler`
  and `Serve`).
- An HTTP transport carrying the same messages (for sidecars and central DNS services) can
  be added later without a new protocol version.

This refines ADR-0007 for challenge solvers only: ADR-0007 deferred out-of-process
connectors to M6 behind gRPC plugins. DNS solvers get a smaller exec protocol now; other
connector kinds keep the ADR-0007 plan and can reuse this pattern.

*As built:* `rfc2136` is implemented on `miekg/dns` (already a dependency) with TSIG
hmac-sha256 or stronger, instead of lego's `dnsupdate`, which would add 15 modules
including a Kerberos stack to the agent. GSS-TSIG (Active Directory DNS) is left to plugins.

**Control plane**
- A deployment has `challenge: http-01 | dns-01` (default `http-01`). Creating a dns-01
  deployment needs an agent that reports at least one solver. Coverage of each name is
  decided by the agent, because CNAME delegation is only visible in DNS.
- The challenge type is part of the approved spec. `SpecVersion` 2 adds it. HTTP-01
  deployments keep the version 1 encoding, so their existing approvals and digests stay
  valid. Moving a deployment to DNS-01 changes the digest and needs a new approval.
- The solver name is not part of the spec. It is local and holds no authority beyond
  the host's `allowed_sans`.

**Wildcards**
- Allowed only with DNS-01.
- A wildcard SAN must appear literally in `allowed_sans`, checked by both the control plane
  and the agent. The pattern `*.example.com` keeps matching single-label names as before,
  but `www.example.com` in the allowlist never permits `*.example.com`.

**Failure handling**
- lego checks propagation against the zone's authoritative servers before answering the
  challenge, with a bounded wait. `resolvers` sets the servers used for CNAME lookups and
  the recursive check; the authoritative servers' own names are still resolved through
  the system resolver.
- Records are removed after every attempt. A crash can leave a TXT record behind; it is
  harmless and is replaced on the next attempt.
- DNS API errors are reported with their class (auth, rate_limited, transient) like other
  issue failures.

## Industry practice (surveyed 2026-11-21)
| Who | DNS provider model | Where credentials live |
|---|---|---|
| [DigiCert Trust Lifecycle Manager](https://docs.digicert.com/nl/trust-lifecycle-manager/connectors/dns-integrations.html) | DNS integrations are connectors | Entered in the central console; optional just-in-time fetch from a password vault |
| [Keyfactor](https://keyfactor.github.io/integrations-catalog/integrations/azure-azuredns-dnsplugin) | Separate DNS plugins per provider | Service principal, or ambient identity (managed identity) |
| [Venafi / CyberArk](https://docs.venafi.com/Docs/currentSDK/TopNav/Content/SDK/WebSDK/r-SDK-Credentials-Programming-Interfaces.php) | Central credential objects used by connectors | Central platform |
| [cert-manager](https://cert-manager.io/docs/contributing/dns-providers), [ExternalDNS](https://github.com/kubernetes-sigs/external-dns) | Few built-in providers; new ones only as external webhooks | Kubernetes secrets next to the solver |
| [lego](https://go-acme.github.io/lego/dns/exec), Certbot, acme.sh, [Caddy](https://pkg.go.dev/github.com/caddy-dns/acmedns) | Built-in providers plus exec/hook/module extension | On the host that runs the ACME client (env or file) |

Pluggable providers are the norm at every size, and new providers increasingly live outside
the core. Credentials split by architecture: platforms that run validation centrally keep
them centrally (often with vault or ambient-identity options), while clients that run on
the host keep them on the host. Certloom runs ACME on the agent (ADR-0006), so host-local
credentials follow the host-client pattern. Central management, which business buyers
expect from DigiCert-class products, is the gap; it is planned as a credential source for
the same solver model (vault reference or ambient cloud identity, resolved just in time)
rather than as a different design.

## Consequences
- Rotating a DNS credential is a host-level change (config management, systemd
  credentials). A central option can be added later as a credential provider without
  changing the agent's solver model.
- The integration matrix gains an evidence column (unit, mock API, local server, live) so
  "supported" says what kind of test backs it.

## Verification
- Plugin protocol: unit tests with test plugins (success, error classes, timeout, bad
  JSON, oversized output, wrong hash, writable file), and the conformance tester run
  against `certloom-dns-lego` with its in-memory test provider.
- Unit tests: solver selection (longest suffix, CNAME target, no match), config
  validation, wildcard allowlist rules on both sides, spec digests (HTTP-01 v1 digest
  unchanged, DNS-01 in v2).
- Cloudflare: lego's provider against an `httptest` server through its base URL, for
  create, delete, bad token and rate limit. An opt-in live test
  (`CERTLOOM_CLOUDFLARE_LIVE=1`) runs against a dedicated test zone.
- Docker e2e: Pebble validating through a real BIND server updated over RFC 2136 with
  TSIG, issuing a wildcard and a CNAME-delegated name, and a renewal.
