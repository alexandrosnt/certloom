# ADR-0006: ACME implementation (M2)

**Status:** Accepted (2026-11-21)

## Context
ACME (RFC 8555) is the first issuance protocol. ARI (RFC 9773) has to be used wherever a
CA advertises it. Writing our own ACME client is hard to justify while maintained libraries exist, so we
use one. We also never take over existing Certbot lineages.

## Facts (checked 2026-11-20)
- **go-acme/lego:** MIT licence.
  - v5 is current (`github.com/go-acme/lego/v5`, v5.6.0, 2026-10-28). v4's last release was v4.35.2 (2026-04-24).
  - ARI is supported in the library: `Certifier.GetRenewalInfo`, `RenewalInfo.ShouldRenewAt`, and `ReplacesCertID` on obtain requests.
  - `RenewOptions.UseARICertID` was added in v5.5.0.
  - ACME profiles are supported through a `Profile` field.
- **Pebble v2.10.3** (Let's Encrypt's test CA):
  - `renewalInfo` is always enabled (GET only), and it validates `replaces` on newOrder.
  - Profiles are configurable (`default`, `shortlived`).
- **Certbot** has used ARI automatically in `certbot renew` since 4.1.0 (2025-06-10).
- **Let's Encrypt:** the default `classic` profile issues 90-day certificates. The `shortlived` profile (~160 h) is opt-in and generally available. `tlsserver` issues 45-day certificates.

## Options considered
| Option | For | Against |
|---|---|---|
| **A. lego v5 library inside the agent** | Maintained, MIT, ARI + `replaces` + profiles, HTTP-01/DNS-01/TLS-ALPN-01 and a large DNS-provider set for M3 | We must track a fast-moving major version; we get only what lego exposes |
| B. ACME client in the control plane, CSR from the agent | One place for account keys | Account keys and DNS credentials get concentrated in the control plane; HTTP-01 needs the agent anyway |
| C. Drive Certbot as the issuance engine | Already installed on many hosts | We lose control of the state machine, the checkpoints and the error classification; we would end up parsing CLI output |
| D. Our own ACME client | Full control | Hard to justify next to maintained libraries; correctness and security risk |

## Decision
Option A, targeting **lego v5**, pinned to a minor version and wrapped behind our
`Issuer` interface (ADR-0007). Upgrades go through the contract-test suite against Pebble.

- **Account keys** stay on the agent or agent-group host, separate from leaf keys, and are never reused as certificate keys.
- **Challenge type:** M2 supports HTTP-01 via an Nginx-served webroot only. DNS-01 and EAB arrive in M3.
- **ARI polling** runs in the control plane. ARI GET requests are unauthenticated and need only the certificate ID (computed from the certificate's AKI and serial).
- **Replacements:** a new order includes `replaces` whenever a predecessor is known and the CA advertises ARI.
- **Fallback timing** when ARI is absent follows ADR-0013.
- **Certbot lineages** under `/etc/letsencrypt` are discovered **read-only**. The platform reports their renewal configuration and ARI-capable version (>= 4.1.0) but never modifies them. Migrating a lineage to platform management is a later, explicit, opt-in workflow.

## Verification
Pebble in CI:
- ARI window present, so the scheduler uses it;
- `replaces` is accepted, and rejected on a second replacement attempt;
- ARI response invalid or unavailable, so the fallback is used;
- `Retry-After` is honored;
- the `shortlived` profile is used to exercise short-lifetime scheduling.

Manual check against Let's Encrypt staging before calling it supported.
